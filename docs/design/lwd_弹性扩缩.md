# LWD 弹性扩缩容 —— 修改内容直白说明

> 配套文档：重启/断线自愈见 `lwd_动态建链.md`；增量契约细节、测试清单与英文设计见
> `lwd_topology_update.md`。本文用大白话回答"弹性扩缩到底改了什么、不改会出什么事"。
>
> 弹性扩缩解决的总问题：**yaml 换一份，运行中的边/云不用重启，新实例拉起后自动接入、
> 请求自动分流到新云。host RoCE 专属，HCCL 一行不动。**

---

## 一、公共机制（三个场景共用）

主题一句话：**让运行中的引擎"安全地发现并接受一份更大的计划"，坏了不连坐、拒了不停服。**

**1. 计划书就是唯一事实（yaml 拓扑文件当共享数据库）**
扩缩容的真相只有一份：yaml 拓扑文件。不加接口、不加 DB——扩容 = 原子替换文件（先写临时名再
rename），边、云、新实例都从它读。谁的机器上谁读自己的副本，所以**每台主机都要替换**。

**2. 门卫看表（mtime 轮询 + 角色感知门）**
每个引擎一条 1 秒的轮询线程，只 stat 文件修改时间；变了就往引擎输入队列塞一个 WAKEUP
哨兵。轮询线程除此之外什么都不干——读文件、验证、比差异全在引擎线程（唯一写者）。
门按场景开：edge_share 只有共享边看，cloud_share 只有共享云看，lwd_cluster 两边都看；
**device comm（HCCL）永远不看**，这条门是弹性功能与 HCCL 互不干扰的第一道闸。
原子替换窗口里文件可能恰好读不到——因此需要 OSError 防御，记一条日志继续
按老计划服务，而不是把引擎炸了。

**3. 五条收货规则，既有实例无豁免（增量契约）**
换上来的文件不是照单全收，diff 五条全过才叫"增量"：场景不变（R0）；全局块冻结——
deployment/feature_ctrl/control_plane 一字不许动，qos 例外是部署保证不是代码保证（R1）；
**既有实例字节不变（R2）；链路只加不减（R3）；新增形状按场景（R4**——edge_share 整对加
且新链不许跨新旧实例，cloud_share 只加边且每条新链必须打向既有云，lwd_cluster 全联接
由标准校验保证**）**。R2 没有豁免：`control_url_map` 已废弃，写出该字段会在解析时直接
拒绝；新云的协调地址放在新云自己的 DP 块中，显式 `coord_url` 优先，否则由 `addr` 和
`coord_port` 派生，不需要也不允许为扩容改动既有边实例。

**4. 同一份变更只处理一次（digest 记账）**
以 canonical digest 记账：mtime 变了但内容语义没变（只改了注释），一条日志了事，不
误触发。拒收也记账——同一份坏文件不会反复刷屏；修好再换，digest 一变自然重新过秤。

**5. 半量应用 + 幂等重试（坏了不连坐）**
一条新连接分两半建：**控制面**（DEALER 创建、握手、路由账本登记）先建；**数据面**
（UCX 通道对）后建，建成才算"armed"、才进路由候选。数据面被拒（内存预算、装配失败）
不回滚控制面：连接保持"仅控制面"，准入门禁用真实理由拒它，**下一个检测到的增量只补
数据面那一半**。每半都幂等——同一增量重放不重复建。apply 钩子里的实例
过滤只认**场景和自己的 instance_id**，不能拿启动快照当过滤依据：启动快照不含
要新加的东西，按它过滤会把扩容要加的连接整个丢掉。

**6. 一盏一盏的灯（error 级观测链）**
设备日志只收 error 级，所以弹性链路的每一跳都是 error：增量检测/拒收/探针注册（带
URL 和轮转表）/控制面应用/数据面构建开始与耗时/armed/探针失败（带目标云和 URL）/
冷却进入/preferred 异常。换文件后按顺序对照，断在哪一跳一眼可见；有"构建开始"没有
"armed/refused"= 卡在 UCX 构建，引擎线程在等它。每请求一条的"request routed"和每批
一条的"range notify received"是排障期临时件，验证完已降回 info。

## 二、edge_share（共享边按"边-云对"扩）

主题一句话：**跑着的共享边引擎，收下新的边-云对，新前端和新云谁都不用重启已有进程。**

**1. 控制面运行期开线（DEALER 不限时）**
原来边到云的 DEALER 只在启动时建。改成运行期可加：`add_link` 把新端点排进一个
SimpleQueue，控制面 IO 线程在下一拍排空建线——**建线动作不占引擎线程**，请求照常进。

**2. 数据面 connect-out，装配成败两说**
新云方向的 UCX 通道对（UP 发、DOWN 收）在引擎线程经钩子构建；预算不够当场拒，连接留
在"仅控制面"，门禁替它挡客，下个增量再试。UCX 连接是惰性的：云还没起完就换 yaml 也
不拒——云起来后第一波 UP 帧的 UHC1 握手自然完成。

**3. 探针目标注册（新连接的 URL 从哪来）**
URL 来自新云自己的 DP 块：显式 `coord_url` 优先；未显式填写时，拓扑解析根据云 DP 的
`addr + coord_port` 派生。没有协调端点的 DP 不注册探针目标。注册接口是
`register_connection(connection_id, url)`，目标粒度包含 edge/cloud/DP，不使用已废弃的边侧
`control_url_map`。

**4. 装好了才开门（arm 才进路由候选）**
仅控制面的连接不是路由候选，准入门禁按"control plane only"理由精确拒绝——不让路由
器去给一条没有传输的链路打分。

**5. 前端报名按内容对账（frontend_digest 拆分 + 容量 8）**
前端 attach 的对账摘要不再包含实例清单——扩容加了实例不该让 attach 校验炸掉；报名
数量按容量上限 8 校验（`LWD_API_MAX_FRONTENDS`），不按当时实例数——先起前端后扩实例
不报错。

**总结：运行期开线（1）、装配两说不丢线（2）、探针 URL 两来源（3）、装好才开门（4）、
前端按内容对账（5）**——共享边加对加云，旧实例零重启。

## 三、cloud_share（共享云按边扩）

主题一句话：**跑着的共享云收编后来的边：白名单放行、监听口复用、提示队列配对。**

**1. 白名单开门（allow_edge 原子超集交换）**
握手白名单原来启动时算死。改成可运行期追加：一次 frozenset 超集交换（复制写），IO
线程要么看到旧集要么看到新集，永不分叉。后到的边靠"报到永不停"（动态建链的周期
HELLO）下一拍自动接上。

**2. 数据面走 RPC，不走钩子（进程边界）**
UCX 监听口、token 路由表都在 **Worker 进程**里（MultiprocExecutor），EngineCore 进程
里的钩子注册表够不着 Worker，因此云侧不能复用边侧的进程内钩子。当前通过
`collective_rpc("lwd_build_runtime_connection")`：端点 Worker（持有共享监听口的那个）
干活返回 True，其余返回 None——**"不是我的活"和"拒了"是两回事**，any(True) 才算建成。

**3. serve 侧复用共享监听口**
云的收件口 init 时就绑好，扩边不重绑；serve 半边的 token 经 `serve_via` 在锁内注册进
路由表——重试中的边下一次 UHC1 握手直接完成，不需要"等下一个窗口"。

**4. 提示/完成 MQ 运行期配对（hint/done）**
后到的边也要早收提示。引擎运行期创建 hint MQ、注册发送器；**句柄必须经 RPC 显式传给
Worker**——环境变量只在启动继承时有效，运行期跨不过进程边界。Worker 侧附加/创建
per-connection MQ 后把 done 句柄传回。早收循环
的一次性快照改成**每拍 `tuple()` 快照**——运行期插入和迭代并发，Python 层迭代会炸，
C 层复制不会（P1 家族模式）。

**5. Worker 状态全量扩展，不只端点**
`_lwd_connections`、`_lwd_up_src_ranks` 在 RPC 回调里对**所有 Worker** 追加；只补端点
Worker 会让非端点在按连接查路由时缺键。

**总结：白名单可加（1）、数据面走 RPC（2）、监听口复用（3）、MQ 句柄显式传（4、5）**
——共享云来一个边收一个，不重启。

## 四、lwd_cluster（边、云各自扩，全联接）

主题一句话：**每个实例都是独立引擎、都看同一份文件、只应用自己的那一份；扩容后请求要
真的流到新云，扩容后死云要真的不吃流量。**

**1. 两边都看门**
lwd_cluster 没有共享侧——边引擎和云引擎都开 watcher，各自收自己的增量。

**2. 每引擎只应用自己的连接（场景过滤）**
边侧 apply 按场景：只有 lwd_cluster 过滤，判据是 `edge_id == instance_id`（身份判断，
不是启动快照判断）；云侧按 `cloud_id == instance_id`。同一次文件变更，边0、边1、云0、
云1 各建各的，互不越界。

**3. 探针轮转运行期扩容（调度到新云的核心）**
探针管理器的目标集合在启动时建立；若不显式扩展，后续云即使完成建链，也不会进入
探针及路由偏好。当前按连接扩展：健康轮转表调用 `add_target((cloud_id, dp_idx))`
（原子 tuple 交换，并发读不撕裂）；探针管理器调用
`register_connection(connection_id, url)`（首次注册生效）。`submit()` 将健康轮转与当前边
可见连接求交后选目标，URL 和块大小重建都按 `LwdConnectionId` 查同一目标表。探针对死云
自愈：3 次失败进 60 秒冷却，冷却完探一拍成功即恢复全员轮转；全员冷却才 fail-open。

**4. 探针 URL 来自云 DP**
同 edge_share 第 3 条：显式 `coord_url` 优先，否则由该 DP 的 `addr + coord_port` 派生；
不使用边侧 map，也不借用边启动 URL。首次注册生效——同一增量重放不改写。

**5. 部分死亡路由（2026-11-20，云停掉后请求不能一半失败）**
风险场景：2边2云 里停掉云 1，若路由候选不剔除死云，边 1 约一半请求仍会轮到云 1。
链路各环节其实都对：10 秒没点
名判失联、拆
数据线、门禁放行（边 1 还有健康的云 0，按设计不该拒）、探针冷却把云 1 踢出探针目标
——但探针失败后偏好为空，**轮询候选集里没有剔除死云**，约一半请求照样轮到云 1，传
输失败被中止。修复：`LwdHeartbeatMonitor` 在**单一事件出口**发布不可变
`LwdHeartbeatVerdict`，判死和心跳恢复两个转换点都只走这一个出口；调度器订阅
`verdict.silent_routes`（`lwd_update_silent_routes`，一次原子 frozenset 交换）；
路由候选剔除静默路由，
**全员静默才回退原集合**（稳态的全静默由门禁在准入时拒绝，这里只兜"准入后瞬间死光"
的竞态）；探针偏好指向死云同样回落到活云。**探针侧同构**：探针管理器订阅同一个
verdict 的**云粒度**静默集——全静默的云不再被探（否则每次冷却到期吃 3 次快失败探针、
相关请求丢失探针偏好、error 日志每 60 秒刷一轮），心跳一恢复自动归队。云粒度 =
该云**所有已采纳路由**都静默：任一 DP 心跳活着探针就继续探（协调 HTTP 监听随实例
进程活着）；还没采纳任何路由的云不排除（监听口可能已起、握手还没完成）。云重启回来，
心跳一恢复，路由排除和探针排除一起自动解除。探针管理器自己**不保存**第二份静默集：
`set_silent_clouds` 把云粒度展开成 `(cloud_id, dp_idx)` 后交给 `LwdCloudHealthTracker`
（一次 frozenset 原子交换），由 `candidates(scope=..., exclude_silent=True)` 统一按
"冷却 fail-open → 可见范围 → 静默 fail-open" 的顺序过滤；`next()` 仍只做冷却轮转，
避免同一过滤被应用两次。心跳状态由 monitor 独占，引擎只做装配与订阅；硬判定
（门禁、路由剔除、拆链）读 monitor 的只读接口，不读 tracker 的候选集——tracker
只缓存 verdict，不参与检测。

**总结：两边都看（1）、各建各的（2）、轮转可扩（3）、URL 两来源（4）、死云不吃流量（5）**
——yaml 一换，新云进轮转；云一死，流量全走活云；云一活，自动归队。

## 五、三个常见追问

**Q1：这么多改动，影响 HCCL 吗？**
**不影响，设计上就是隔离的。** watcher 门第一判据就是 `data_plane_comm == host`——
device comm 下增量检测、应用、探针注册一行都不执行；`_lwd_apply_topology_increment`
里的所有分支都在这条门内。共享路径还需要满足以下等价条件：探针管理器在 device 部署也会执行，
但单 URL 部署的目标、URL、completion 语义与改前逐值等价（只是健康记账从无到有，
轮转结果不变）；路由静默过滤在 device 下静默集合恒为空，等价于不存在。共享代码里
只有两处非弹性改动：一处是无害的方法调用补充，一处是 FileStore 超时修复
（`--distributed-timeout-seconds` 原来根本传不到预创建的 FileStore，device 部署同样
受益）。每次改动都按"对 hccl 完全无影响才允许共用"过秤。

**Q2：扩出去的，缩得回来吗？缩容的操作流程是什么？**
**缩容 = kill 成员，yaml 随你怎么改，引擎都继续活。** R3 链路只加不减、R2 实例不许
删——把成员从 yaml 里删掉的 diff 会被**拒收，这是故意的且无害**：引擎继续按"成员
全集"计划服务，死成员由 liveness 管理（10 秒没点名判失联 → 拆线、门禁拦新请求 →
路由和探针都剔除死云 → 流量自动归到存活云），每个引擎每个文件版本只打一条拒收日志
（digest 记账不刷屏）。完整流程：**kill 成员 → 改 yaml 删成员（各引擎一条拒收日志，
幸存者照常服务）→ 再改 yaml 加回来 + 拉起成员进程 → 正常扩**——重新扩照常识别增量
（diff 基准是启动拓扑、从不前进），同 id 复用靠幂等键不重复建链不重复记账，成员进程
重启靠"报到永不停 + 心跳恢复"自动归队。换句话说：**加，走弹性增量；
减，走 kill + liveness（路由/探针/门控三处静默处理）**。当前分支的设备验收需单独执行，
不能沿用历史分支结果——不
需要"yaml 驱动引擎主动断链"的第三条路，也避开了排水协调（在途请求排空）那一整坨
复杂度：kill 后最多 10 秒检测窗内在途请求被容错中止，客户端重试全走活云。

**Q3：还有多少条 error 日志是临时的？**
临时件已清理完：每请求的 `request routed`、每批的 `range notify received`，以及
`engine assembled`/`waiting for cloud handshakes`/`watch up`/`cloud-params verified`
这类一次性启动日志，都已降回 info。留在 error 的都是稀有事件（增量检测/拒收/探针
注册/构建开始与耗时/armed/探针失败/冷却进入/preferred 异常），设备上值得看、长期
保留也不吵。
